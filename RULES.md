# DevDay Kochi Hackathon: Rules

This repo is an entry to the DevDay Kochi hackathon. These are the rules
the team builds under.

## Track

**4. MAKE ROOM FOR PLAY**

> Build something people want to *experience*, not just use. A game or
> playful experience shared by everyone in the room.

## Ground rules

1. **Build during the event.** All project code is written during the
   hackathon window. Open-source libraries and public-domain assets are
   fine; pre-built project code is not.
2. **Teams.** Work as a team of up to the size set by the organisers.
   Every member must be able to explain any part of the project.
3. **AI tools are allowed, and must be disclosed.** Log every AI tool,
   model and role in [AI_USAGE.md](AI_USAGE.md), updated in the same
   commit as the work it describes.
4. **Show your work.** Commit early and often (roughly every 30 minutes)
   and keep [CHANGELOG.md](CHANGELOG.md) current. The git history is part
   of the judging evidence.
5. **Licences and credits.** Respect the licence of every asset and
   dependency, and credit them in the README.
6. **No secrets.** No API keys, tokens or credentials in the repo.
7. **Demo what works.** The demo must run live from this repo. Clearly
   label anything mocked or not finished.
8. **Be kind.** Follow the event code of conduct. Organiser decisions are
   final.

## Submission checklist

- [ ] [SUBMISSION.md](SUBMISSION.md) filled in
- [ ] [README.md](README.md) has a working quick start
- [ ] [CHANGELOG.md](CHANGELOG.md) and [AI_USAGE.md](AI_USAGE.md) are
      current with the final commit
- [ ] Screenshots committed under `docs/screenshots/`
- [ ] Demo rehearsed on real phones on the venue Wi-Fi

## Judging (what we optimise for)

- **Play:** do people in the room want to do it again?
- **Clarity:** can a first-timer understand it in three seconds?
- **Craft:** does it feel finished, fast and polished on a phone?
- **Technical execution:** does it hold up with a full room?
